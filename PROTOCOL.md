# Command Center server protocol

The server listens on loopback and serves the local UI over HTTP. The browser connects to the same host with a WebSocket. Requests and events are JSON objects with a string `type`. The server validates message envelopes, tab and slot identities, payload values, and HTTP/WebSocket Host and Origin headers.

## App key

Host and Origin checks only stop other websites; any local process can send those headers. Every connection also needs the **app key**: 32 random bytes as 64 hex characters, made fresh on each app start. Electron makes it, passes it to the server as `CC_APP_KEY`, and hands it to the page through the preload bridge (`window.cc.appKey()`); it is never in a URL, a log or a file. A bare `npm start` makes its own key and prints one line, `Open http://127.0.0.1:<port>/#key=<key>`; the page reads `#key=` from `location.hash` and removes it with `history.replaceState`. The server reads `CC_APP_KEY` once at startup and deletes it from its environment, so no child process inherits it.

- WebSocket: `ws://<host>/?key=<key>` (a browser page cannot set upgrade headers). A missing or wrong key is refused with `403` in both the `verifyClient` check and the `upgrade` handler.
- HTTP: every non-`GET`/`HEAD` route (`POST /api/paste-image` and `/api/paste-file`; any other `POST`, including the retired `/api/avatar`, is refused `403` without the key and `405` with it) needs the header `X-App-Key: <key>`; missing or wrong is `403`. `GET` of the page files stays open so the page can load and read its key. `/api/leader-mcp/<tab>` keeps its own per-leader bridge token.
- The comparison is `crypto.timingSafeEqual` on equal-length buffers; no key set means nothing matches.
- Every HTTP response (static files, uploads, avatars, errors) carries `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` and `X-Content-Type-Options: nosniff`, so a website cannot frame the app.

## Initial state and selection

The client sends `{ "type": "hello" }`. The server replies with a `state` message followed by `chatHistory` for the selected tab. Hello does not start a leader session. `selectTab` changes the selected tab and sends that tab's transcript to the requesting client.

```json
{
  "type": "state",
  "selectedTabId": "sample-development",
  "projects": [
    {
      "id": "sample",
      "name": "Sample",
      "folder": "C:/work/sample",
      "tabs": [
        {
          "id": "sample-development",
          "name": "Development",
          "kind": "dev",
          "setupName": "Fixed crew",
          "folder": "C:/work/sample",
          "crew": [],
          "lookPause": false,
          "steps": [],
          "fixedCrew": { "version": 1, "preferences": {}, "roleExtras": {}, "busy": {}, "notices": {} },
          "fixedTask": null,
          "runs": [],
          "processState": {},
          "derived": {},
          "leaderStatus": "not-started",
          "permissionMode": "accept",
          "permissionAction": null,
          "pendingRequestCount": 0,
          "changes": { "repo": false, "branch": null, "ahead": 0, "behind": 0, "lastCommit": null, "uncommittedFiles": [] },
          "notes": { "path": null, "content": "", "truncated": false },
          "chatRevision": 0,
          "savedRevision": 0
        }
      ]
    }
  ],
  "fixedCrewDefinitions": [],
  "crewDefaultsVersion": 1,
  "modelOptions": {},
  "effortOptions": {},
  "opencodeModels": [],
  "claudeModels": [],
  "discoveryInfo": {},
  "clientPrefs": {},
  "globalWork": [],
  "clis": [],
  "acpClis": [],
  "settings": { "tools": {}, "github": {}, "vault": {}, "folders": {}, "skills": {}, "permissionModes": {}, "permissionActions": {}, "uploads": {} },
  "requests": [],
  "pendingRequestCounts": {},
  "requestActions": {},
  "launchSafety": { "blocked": [], "uncertain": [], "released": [], "notices": [] },
  "releasedProcesses": []
}
```

The example omits fields for brevity. `clis` is the capability table of every CLI the server knows, `{ id, label, advisor, readOnlyEnforced, customModel, installed, models, efforts }`: one row each for `claude`, `codex` and `opencode`, and one `acp:<id>` row per CLI added in Settings. **Fixed crew (what the page uses).** Every tab has the same 18 fixed positions, in this order and with these ids (`slot`): leader, planner, researcher, coder, designCoder, helper, imageMaker, socialMaker, videoMaker, secondOpinion, reviewer1, fixer1, reviewer2, fixer2, final, designFinal, minimalFixer, minimalReviewer. The top-level `fixedCrewDefinitions` lists them as `{ slot, label, canWrite, reviews?, group }` (`group` is Planning, Making or Checking; `reviews` names the position whose work a reviewing position checks), and `crewDefaultsVersion` is the version of the built-in position instructions. A fixed tab (a tab with a `fixedCrew` field) is saved with `setupName: "Fixed crew"`, `crew: []`, `steps: []` and `lookPause: false`, and carries:

- `fixedCrew`: `{ version: 1, preferences, roleExtras, assignmentsDigest, notice?, busy, notices }`. `preferences[slot]` is `{ assignment, source }`: `assignment` is `null` (no model, the position cannot run) or `{ cli, model, effort, advisor? }` and nothing else (no picture, role, write flag or runtime field), and `source` is `"user"` for a choice the user made or cleared and `"auto"` for one the server filled. `assignmentsDigest` is the server digest of all current assignments and their sources, used to reject stale bulk changes. `roleExtras[slot]` is the user's extra instruction text for a position (at most 8192 bytes, no control characters). `busy[slot]` is true while that position has a working run, while the tab is saving and, for the leader, while a turn is active or an approval is pending. `notices[slot]` (reviewing positions only) is `{ status, blocking: false, message }` where `status` is `unassigned`, `same-model`, `same-company`, `different-company` or `unknown`: advice about review independence, never a block. `notice` is a plain-words recovery note when the server had to replace damaged crew settings with fresh ones. When the crew cannot be used, `fixedCrew` is instead `{ version, unavailable: true, notice }` (the workspace is blocked by an unfinished recovery, or the crew was saved by a newer version): the page shows the notice and offers no crew changes.
- `fixedTask`: `null` or the summary `{ taskId, planVersion, detailRevision, stage }` of the tab's saved task, or `{ blocked: true, notice }` when it cannot be read safely; the whole record is read with `getFixedTask` (see "Fixed crew messages").

Each tab is its saved workspace tab plus the fields below. The saved tab also carries `setupName: "Fixed crew"`, `lookPause: false` and `steps: []`, which only keep the file's shape and always have those values.

- `crew`: the positions that have a model, each `{ slot, name, role, canWrite, isLeader, cli, model, effort, advisor? }` plus a tab-scoped `seatKey` (`<tabId>.<slot>`), live `status`, `task`, and the ids of its working `runs`. `name` and `role` are the position's fixed label. `cli` is `claude`, `codex`, `opencode` or `acp:<id>` (a CLI added in Settings). `advisor` (a Claude model) is only on a position whose CLI supports one. A position with no model is not in the list. The personal picture is not here: it is the client preference `avatar`.
- `runs`: process-engine run records with `runId`, `seatKey`, captured output, usage, stall state, and launch source.
- `processState`: the tab's `server/process.ts` state, the positions' status and the run snapshots. `derived` contains its `workingSeats`, `runViews`, `leaderTurnActive` and `busy` views. `busy` is true while any position is `working`, any run is working, a leader turn is active or a Save is queued or running.
- `leaderStatus`: `not-started`, `ready`, or `dead`; plus optional `leaderUsage`, `leaderActivity` (what the leader is doing now, or `null`) and `leaderJobs` (the background jobs a Claude leader's CLI is running).
- `chatRevision` and `savedRevision`: transcript revision counters. A transcript that cannot be read costs only its own tab: both are `0` and the tab carries `chatProblem` (the reason); every other tab and the rest of the state are unaffected. That tab still opens, with an empty history at revision `0`; a `chat` to it is refused, and Clear keeps the damaged file as `<tab>.jsonl.bad-<time>`, starts an empty chat and sends `chatCleared` with `noUndo: true`.
- `activeWork`: true while the tab has something the app would cut off by closing: a running worker, an active leader turn or a Save, or an unconfirmed process (`launchSafety.uncertain`) of this tab. The page asks before the app closes while any tab has it.
- `permissionMode`: this tab's saved `ask`, `accept`, `plan`, or `bypass` choice. Missing entries default to `accept`, except after the app recovered from a damaged settings file: then they are `ask` until the owner picks a mode for the tab.
- `permissionAction`: latest permission change and its server-owned `requestId` and status.
- `pendingRequestCount`: pending requests addressed to this tab.
- `changes`: read-only local git summary, recomputed on tab select and after a run finishes. A non-repository is `{ "repo": false }` with empty details.
- `notes`: capped contents of `<tab folder>/.command-center/<tabId>/RESUME.md` (until the tab has saved one, the folder's older shared `<tab folder>/.command-center/RESUME.md`, read only), or empty content when missing. `truncated` reports the 64 KiB limit.

`settings` contains Claude, Codex, OpenCode, and Gemini CLI versions and sign-in status, GitHub CLI status, the optional vault path and default project folder, and per-CLI instruction/skill/MCP/plugin inventory. Gemini is install-only: its sign-in status remains unknown, its inventory contains only `~/.gemini/GEMINI.md` and the selected project's `GEMINI.md`, and the server does not call Gemini auth or MCP commands. Settings are persisted at `<data root>/settings.json`; requests are persisted at `<data root>/requests.json`. `installed` and `signedIn` are `true`, `false`, or `null`; `null` means unknown, never guessed. Inventory keeps server names and parsed version/account fields only, never raw CLI output or tokens. The latest settings action is in its target's `action` field with `requestId`, `status`, and `message`; preference changes use `preferenceAction`, tab permission changes use `permissionActions`, and uploads use `uploads`. `requests` contains persisted cross-tab requests with `pending`, `accepted`, `declined`, or `destinationRemoved` status. `pendingRequestCounts` is keyed by destination tab id. `requestActions` keeps all running asynchronous actions plus the latest 32 finished actions keyed by request id. A running action is never evicted, so a client treats a pending id it saw listed that later disappears, or that a post-reconnect snapshot does not list, as finished (`unknown`, never Working). Clients otherwise retire pending ids on a terminal `done`/`failed` result or snapshot, and retain the latest terminal result per control.

The server sends a full `state` after a change. State is shared across connected clients; transcript messages and leader output include their `tabId`. Each tab's `derived.busy` includes a queued or running Save, a live worker, a position marked working, or an active leader turn. `derived.leaderTurnActive` is true exactly while that tab has an active leader turn; it excludes worker runs and a queued Save. A running Save uses the leader and therefore counts as an active leader turn. `globalWork` is a list of plain-language reasons the app has work that belongs to no tab (a running Settings action, an upload in flight, an unconfirmed process from an earlier session): the page adds them to the close warning. Run output and usage appear in `state` only while the run is live. A burst of usage events sends one `state` at once and at most one more per 400 ms. `runs` holds every working run plus the 50 most recent finished runs; older runs are read through `historyList` and `historyRun`.

## Server events

- `state`: current projects, tabs, crew, process state, settings, preferences, and launch-safety state.
- `output`: `{ tabId, runId, seatKey, chunk }` worker output.
- `fixedRunRequested`: `{ tabId, slot }`, the answer to a `run` request: the leader was asked to handle it (see `run`); nothing was started yet.
- `runStart`: `{ tabId, runId, seatKey, cli, model, effort, folder, startedAt, canWrite, launchedBy }`. `launchedBy` is `{ kind: "leader", slot, name }` for a run the leader started, and `null` otherwise. Every run view in the state carries the same `launchedBy`.
- `runFinish`, `runFail`, `runStop`: terminal worker event with `{ tabId, runId, seatKey, outcome, exitCode }`. These events update the tab's process state. The server never stops a run by itself.
- `runStalled`: `{ tabId, runId, seatKey, action }`, where `action` is always `escalate`: a run with no new output for 5 minutes is shown as stalled and the owner is told. The server never stops or restarts it; the owner decides (Stop, or wait), and any new output clears the stalled mark.
- `rateLimit`: `{ tabId, runId, windows }` for a worker limit update.
- `chatHistory`: `{ tabId, messages, revision, savedRevision }`.
- `chatMessage`: one persisted user or assistant message, including `tabId` and `revision`. A user message echoes its optional `requestId`; the id is stored and appears again in `chatHistory`.
- `chatDelta`: `{ tabId, text }` streaming leader text.
- `leaderActivity`: `{ tabId, label }`, what the leader is doing now; `label: null` means the activity ended and is cleared. The same value is `leaderActivity` (or `null`) on the tab in `state`.
- `chatDone`, `chatError`: end of a leader turn, with the latest transcript revision and saved revision. `chatError` may include `message`.
- `chatNotice`: `{ tabId, message }`, a note about a leader process that belongs to no turn (for example, "Could not confirm the old Codex leader stopped"). The client shows the text and leaves the running turn, its streamed draft and the busy state alone; `chatError` is only for a failed turn.
- `folderBusy`: `{ action: "chat" | "run", tabId, requestId?, items: [{ tool, agoSeconds, writer? }] }`, the answer to a `chat` or `run` that was held because another agent is working in the tab's folder. Nothing was saved or started. `tool` is `Claude Code`, `Codex` or `OpenCode`, or `null` for files that changed with none of Command Center's own agents working there. An item for another Command Center tab's writing run has `tool: null` and `writer: { seatName, roleLabel, tabName }`. `requestId` is the held chat's. The page shows the list with Continue anyway and Cancel, and Continue anyway repeats the message with `confirmBusy: true` under a fresh request id. A session counts when it was active in the last 2 minutes in this folder, a folder inside it or one that contains it; Command Center's own leader and crew sessions never count, and another Command Center tab counts only through a `writer` item as above (a read-only position never does). A run the leader starts is never held: it posts one quiet line in the tab's chat per outside session per 10 minutes, and the launch notice keeps the text.
- `steerRefused`: `{ tabId, requestId?, reason: "approval" | "save" | "starting" | "unavailable", message }`, the answer to a `steer` the server did not push into the running reply. Nothing was saved or sent; the client keeps the message where it was queued. A `chatMessage` that carries `split: true` is the reply so far, written down because a steer follows it: the client drops its streamed draft.
- `chatCleared`: `{ tabId, revision, savedRevision }` after Clear stops that tab's leader and resets its transcript.
- `chatRestored`: `{ tabId, messages, revision, savedRevision }` after `undoClear` restores the exact transcript snapshot from before Clear.
- `chatUndoRejected`: `{ tabId, reason }`, where `reason` is `expired`, `unavailable` or `busy` (a leader answer or a Save is still running).
- `saved`: `{ tabId, revision, savedRevision }` after the leader writes a handover successfully.
- `leaderLaunch`: persisted launch notice with `{ id, seatId, seatName, brief, source, pending }`. `source` is the leader's current name; `pending` is true only while the server is persisting and attempting the launch.
- `runAccepted`, `killAccepted`, `stopAllAccepted`, `launchBlockCleared`, `launchNoticesAcked`, and `unconfirmedReleased`: direct acknowledgements for the corresponding requests. A clear-block acknowledgement includes `cleared` to report whether a block existed.
- `historyList`, `historyRun`: history query results. `historyRun` echoes the requested `seatKey` and `timestamp` and includes the brief, capped output, byte count, truncation flag, and parsed outcome; clients match replies by `seatKey` + `timestamp`. A history lookup that fails sends a plain `error` with only a `message`: it names no seat, so a client cannot match it to a request and instead gives up on a list or run that stays unanswered for a while (the page waits 15 seconds) and lets it be asked again.
- `actionResult`: `{ action, requestId, ...result }` after a state-changing WebSocket action succeeds. Errors/refusals echo a valid `requestId` and the action.
- `settingsRefreshed`: read-only Settings inventory refresh completed.
- `crewRolePrompt`: `{ requestId, ...the position's built-in prompt }`, the answer to `getCrewRolePrompt`. `crewAssignmentsPreview`: `{ requestId, draftId, fixedCrew }`, the answer to `previewCrewAssignments`; it changes nothing and saves nothing. `fixedTask`: `{ requestId, tabId, task }` (`task` is the saved record or `null`), the answer to `getFixedTask`. `fixedTaskResult`: `{ requestId, tabId, taskId, ...result, executionAvailable: true }`, the answer to a task approval or action request, followed by a full `state`.
- `error`: `{ message }` for rejected requests or failed operations. A request refused synchronously names its `action`, includes a valid `requestId` when present, and includes its `tabId` and/or `projectId` when carried. A refusal from an async action (Settings, permission mode, requests, approvals) carries only `{ action, requestId }`; match it by request id. Errors without `action` (history lookups and background failures) roll back nothing. `chat` accepts at most 8 images and 8 files.

Launch notices are persisted in `state.launchSafety.notices` (the newest 50 are kept). A notice keeps at most 4000 characters of the brief as a reminder; the run itself gets the whole brief (a task brief is accepted up to 200000 characters). `launchSafety.live` (in `launch-safety.json`, not in `state`) lists runs started and not yet seen to end: after a hard crash the next start blocks those seats (clear with `unblockSeat`), because nothing tracks their processes any more; a clean shutdown clears it. An older `launch-safety.json` without the `released`, `uncertain`, `live`, `notices`, `timestamps` or `nextNoticeId` entries is read with them empty; a damaged entry still refuses to start. Existing launch-safety rows using old bare seat IDs remain visible. New worker records use tab-scoped seat keys and run IDs.

## Client messages

Fields shown are required unless marked optional. Invalid or unknown messages receive an `error` event.

| `type` | Fields | Effect |
|---|---|---|
| `hello` | none | Sends state and selected-tab transcript. |
| `selectTab` | `tabId` | Selects a tab and returns its transcript. |
| `addProject` | `requestId`, `id`, `name`, `folder`, `tabId?`, `tabFolder?`, `projectOnly?`, `fixedCrewVersion: 1`, `crewChoices?`, `autoAssign?` | Adds a project with one Development tab, which has the fixed crew: `crewChoices` is `{ <slot>: { cli, model, effort, advisor? } }` for the positions the user picked (each must name an installed CLI and a model and effort from its live lists; OpenCode also accepts a typed provider/model id), `autoAssign` (default `false`) fills the empty rest from the installed CLIs, and any other field is refused. A request id is required. `tabFolder` defaults to `folder`; the form requires `fixedCrewVersion: 1`. |
| `renameProject` | `projectId`, `name` | Renames a project. |
| `removeProject` | `projectId` | Removes an idle project. The last project cannot be removed. |
| `addTab` | `requestId`, `projectId`, `name`, `folder`, `tabId?`, `projectOnly?`, `fixedCrewVersion: 1`, `crewChoices?`, `autoAssign?` | Adds a tab exactly as `addProject` does (positions unassigned unless picked or auto-assigned). An explicit `tabId` that already has a saved chat or run history (a removed tab's id) is refused; a generated id is always fresh. |
| `setCrewAssignment` | `requestId`, `tabId`, `slot`, `assignment` | Fixed tabs. Saves the user's model for one position: `assignment` is exactly `{ cli, model, effort, advisor? }` (no other field), the CLI must be installed and the model and effort must be in its live lists (OpenCode also accepts a typed provider/model id, and the position's own saved model and effort stay valid), and the saved choice is `source: "user"`. The answer is `actionResult` `{ action, requestId, tabId, slot }`; a refusal is an `error` with the same `action` and `requestId`. Refused for a tab that is not the selected one, while that position is working or the tab is saving, and for the leader's CLI, advisor or extra instructions while it is answering or waiting for approval. |
| `setCrewModelForAll` | `requestId`, `tabId`, `cli`, `model`, `expectedAssignmentsDigest`, `confirmReplace` (boolean) | Fixed tabs. Chooses one model for all idle positions, retaining compatible effort/advisor choices. Requires the current state `fixedCrew.assignmentsDigest`; `confirmReplace: true` is required to replace user choices. Busy positions are skipped. Answers `actionResult` with `action: "setCrewModelForAll"`, the same `requestId` and `tabId`, `changed` and `skipped` arrays of `{ slot, label }`, `notice` and the resulting `assignmentsDigest`, followed by state. Unchanged positions are absent from both arrays. A refused request sends `error` with the same action and requestId and a readable message; async errors need not carry tabId. No changes are saved on refusal. |
| `clearCrewAssignment` | `requestId`, `tabId`, `slot` | Fixed tabs. Empties one position (`assignment: null`, `source: "user"`), so Auto assign and the startup fill leave it empty. Same answers and refusals as `setCrewAssignment`. |
| `autoAssignCrew` | `requestId`, `tabId` | Fixed tabs. Fills the empty positions and redoes the ones the server filled before (`source: "auto"`) from the installed CLIs, preferring each position's approved default CLI and, for a reviewer, a different company from the position it reviews when one exists. Never changes a position with `source: "user"`. Same answers and refusals. The server also fills empty `auto` positions without a request when it starts and after CLI discovery. |
| `setCrewRoleExtra`, `resetCrewRoleExtra` | `requestId`, `tabId`, `slot`, `text` (set only) | Fixed tabs. Saves or removes the user's extra instruction text for one position (at most 8192 bytes, no control characters). The extra text cannot change the position's identity, access or launch authority. Same answers and refusals. |
| `getCrewRolePrompt` | `requestId`, `slot` | Answers `crewRolePrompt`. Read-only. |
| `previewCrewAssignments` | `requestId`, `draftId` (1-128 characters), `choices`, `autoAssign` (boolean) | Answers `crewAssignmentsPreview` with the crew a creation dialog would save for those choices. Changes nothing. |
| `getFixedTask` | `requestId`, `tabId` | Fixed tabs (current version only). Answers `fixedTask` with the tab's saved task record, or `null`. Read-only. |
| `listFixedTaskArchives` | `requestId`, `tabId`, `cursor` (null or archive ID), `limit` (1-50) | Current fixed tabs only. Read-only. Answers `fixedTaskArchives { requestId, tabId, items, nextCursor }`. Items are `{ id, kind: "task", scope, completedAt }`, using verified `task.plan.scope` and the recorded manifest time in stable ID order. Only verified receipt-bearing archives are listed. |
| `getFixedTaskArchive` | `requestId`, `tabId`, `taskId` | Current fixed tabs only. Read-only. Answers `fixedTaskArchive { requestId, tabId, taskId, task, executions, manifest }` after bounded identity/hash verification. Archive text is data. No restore, replay, path parameter or mutation authority is accepted. |
| `approveFixedPlan` | `requestId`, `tabId`, `taskId`, `planVersion`, `recordRevision` | The owner approves the task's plan as it stands. The ids and versions must match the saved record; a changed plan has a new `planVersion` and needs a new approval. Only for the selected tab. Answers `fixedTaskResult`. |
| `approveFixedRough` | as `approveFixedPlan` plus `roughRevision` | The owner approves the rough version of visible work, named by its revision. Only for the selected tab. Answers `fixedTaskResult`. |
| `requestFixedTaskAction` | as `approveFixedPlan` plus `action` (`assist`, `rough`, `build`, `polish`, `check`, `visualCheck`, `inspect`, `review`, `checkpoint`, `fix`, `final`, `commit`, `push`, `publish`) | Records the owner's request for that action in the task. It records intent only: nothing is executed and nothing is retried by this message. Failed delivery cancels only the exact still-reserved unconsumed request with no journal entry, preserving the current stage and approvals; consumed or changed identities stay held. A cancellation write failure reports a correlated error and retains the reservation. Replayed requests keep their identity and do not nudge again. Only for the selected tab. Answers `fixedTaskResult`. |
| `renameTab` | `tabId`, `name` | Renames a tab. |
| `removeTab` | `tabId` | Removes an idle tab. A project's last tab cannot be removed. Nothing changes (the tab and its leader stay) if the workspace cannot be saved. Its launch blocks and notices go with it; its chat file stays on disk. |
| `changeFolder` | `tabId`, `folder` | Changes an idle tab's working folder. It stops the old leader and does **not** start a new one: the leader for the new folder starts on the tab's next chat message, so that folder's project hooks never run unasked. |
| `changeProjectFolder` | `projectId`, `folder` | Changes the project's default folder for new tabs. Existing tab folders are unchanged. |
| `run` | `tabId`, `slot`, `prompt`, `confirmBusy?` | The owner's request for work from one position. It does not start a process: the server checks that the position and the leader each have a model, that the leader is not still answering (otherwise it is refused: steer the request into the reply or wait), and holds it with `folderBusy` while another agent is working in the folder (as `chat` is). Then it hands the prompt to the leader as a turn that says it is a request and not permission to skip the saved task and its approvals, and answers `fixedRunRequested`. Anything that really starts goes through the leader's fixed tools (see "Fixed crew tools"), one execution at a time. Every start counts against the launch budget of 8 per 5 minutes, counted per tab; the refusal (`launch budget exceeded: ...`) says when the next one is allowed. Every launch puts the position's fixed role prompt, the owner's extra text for it and the report instructions around the brief; it is in the saved `<seatKey>-<stamp>.brief.txt`. A `Researcher` run also has the web: Claude gets `--allowedTools WebSearch,WebFetch` (probed in read-only plan mode), Codex starts as `codex --search exec`. Workers run at low priority. When the CLI process ends, any process it left running (a dev server, a background shell) is stopped before the run is reported over, and the run's log gets a `[cleanup] stopped N processes this run left running` line. |
| `killRun` | `runId` | Requests a kill for exactly one run and replies with `killAccepted`. The seat is launch-blocked until explicitly unblocked. |
| `stopSeat` | `tabId`, `slot` | Marks the position stopped and requests kills for every active run in that tab slot. A worker position is launch-blocked even when nothing was running. Each live run settles only when its process close is confirmed or it is explicitly released. Also stops that tab's leader session when `slot` is the leader. |
| `killSeat` | `seatId` | Alias for `stopSeat`, using a tab-scoped `<tabId>.<slot>` key. |
| `stopAll` | none | Marks every working position stopped, stops every leader session, requests kills for all worker runs, and replies with `stopAllAccepted`. Live runs settle on confirmed close or explicit release, as for `stopSeat`. A leader's half-written answer is kept in the chat, ending with `(Stopped before it finished.)`. |
| `chat` | `tabId`, `text`, `requestId?`, `images?`, `files?`, `confirmBusy?` | Sends one message to that tab's lazy leader. `requestId`, when present, must be 1-64 ASCII letters, digits, `_` or `-`, starting with a letter or digit. The server echoes it on the persisted user `chatMessage` and on a refusal `error`. Image/file paths must be returned by the upload endpoints and contained in scratch. The leader prompt lists non-image file paths it may read. With `confirmBusy: true` the server quiets the agents the person was last shown (`folderBusy`) for this tab for 10 minutes and sends the message; an agent that was not shown still holds it. |
| `steer` | `tabId`, `text`, `requestId?`, `images?`, `files?`, `confirmBusy?` | Pushes a message into the reply that is running now (Claude: the SDK input stream; Codex: `turn/steer`; OpenCode: a second `prompt_async`). Validated like `chat`; the same folder warning (`folderBusy`) applies. In the same tick the reply so far is saved as an assistant message (`split: true`) and the steer is saved as a user message, so the chat reads [reply so far][steer][rest of the reply]. ## Chat storage and leader lifecycle

Each tab transcript is JSONL at `<data root>/chats/<tabId>.jsonl`. Messages, Clear events, restore events, and saved revisions are replayed at startup. A leader is created only for the first chat on that tab. Leaders run in the tab folder. A Claude leader loads the `user`, `project`, and `local` Claude settings; a Codex or OpenCode leader loads that CLI's own user configuration (the server never writes `~/.codex`, `~/.claude` or `~/.config/opencode`). The server runs no health check at start-up and writes no `leader-check.json`; a leader that cannot start reports its error when the first chat message needs it.

Save requests are serialized per tab (each tab has its own queue; one tab's Save never holds up another tab's). A Save waits for the tab's active leader turn with a timeout, then asks the leader to write `<tab folder>/.command-center/<tabId>/RESUME.md` before updating `savedRevision`. Clear bypasses that queue: it stops the tab leader and resets its active transcript view immediately while preserving the JSONL history. The next leader turn after Clear, and after any other event that leaves a tab with no leader memory (an app start, Stop, a folder or process change, a CLI switch, Undo, a leader that died), is instructed to read the handover before replying; a successful read turn consumes that requirement. Save is refused (`send a message first so the leader reads the saved handover; saving now would overwrite it`) while that read is still owed. If a Save times out but its turn later finishes OK and wrote the handover, the server marks it saved and sends `saved`, which clears the failed card.

Each successful Save also records a "past session" for the leader: one log and one brief file under `logs/` named like a worker run, `<tabId>.<leaderSlot>-<timestamp>.log` (the transcript at Save time, `You: ...` / `<leader name>: ...`, ending with the usual exit marker, status `done`) and `.brief.txt` (`Saved handover: <path of RESUME.md>`). `historyList` and `historyRun` for the leader's seat key (`<tabId>.<leaderSlot>`) return them like any run. The newest 50 are kept per leader, older ones are removed file by file. Removing a tab leaves its chat file and logs on disk and its id is not handed out again; a launch block or notice of its seats is dropped with it.

Clear Undo is tab-scoped and lasts 10 seconds. The server journals a restore event so the restored messages, chat revision, and saved revision survive a restart. An Undo request for a different tab cannot consume another tab's pending snapshot.

### Leader CLIs

The leader seat's `cli` decides what runs it. All three behave the same for chat, Save/Clear, approvals, usage and Stop.

| CLI | Process | Crew tools | Permission modes |
|---|---|---|---|
| `acp:<id>` | the CLI's saved start command (program resolved on PATH outside every project folder, no shell, `.cmd` shims through `cmd.exe` with plain-word arguments only), Agent Client Protocol: JSON-RPC 2.0, one JSON object per line on stdin/stdout, one session | HTTP MCP server `tab-crew` given in `session/new` (the same bridge as OpenCode, a token of its own); a CLI that does not take HTTP MCP servers starts without the fixed tools and the chat gets one notice | Full access only (see Limits) |
| `claude` | Claude Agent SDK, long-lived `claude` child | SDK MCP server `tab-crew` | SDK modes as above |

A mode change is stored and used from the next `turn/start`. |
| `opencode` | `opencode serve` on a free `127.0.0.1` port, password in the `OPENCODE_SERVER_PASSWORD` environment variable, one session | MCP bridge (below), added at runtime with `POST /mcp` | Session rules, last match wins: `*` ask first, then `read`, `glob`, `grep` and `list` allow (looking is free, like Claude's default mode and Codex) with `read` of `*.env` and `*.env.*` asking again, `tab-crew_*` always allow; `accept` adds `edit` allow, `plan` adds `edit` deny, `bypass` allows everything. Only a fixed command line is spawned (`codex app-server`, `opencode serve --hostname 127.0.0.1 --port <n>`) in the tab folder. The model, prompt and every secret travel in JSON-RPC or HTTP bodies, never in argv. The child environment drops `CC_DATA_DIR` and `CC_TEST_FORCE_PACKAGED`. Codex takes the model and effort on every turn; OpenCode takes the model per prompt (`provider/model` is split at the first `/`). Every approval goes through the same browser approval path as Claude: Codex commands are tool `Bash` and file changes `Edit`; OpenCode `bash` is `Bash`, and `edit`, `write` and `patch` are `Edit`; anything else keeps its own name. Requests with no screen (Codex `requestUserInput` and MCP elicitation, OpenCode `question.asked`) are declined, and no request is left unanswered on Stop or exit. Stop interrupts or aborts the turn, then ends the whole process tree; a server shutdown ends leader children too. A server that crashes leaves `logs/.children-<pid>.json`, the list of processes it was watching; the next server start (the server does not listen until this finished, the whole sweep, every file at once, has one 41 s cap (`SWEEP_CAP_MS`: the 30 s process list, the 10 s kills and a 1 s margin); whatever has not finished by then stays in its registry file for the next start, and a failed sweep never stops the start) ends those that are still the same processes, removes the file, and logs `[cleanup] stopped N processes left by an earlier server`.

Starting (spawn, Codex `initialize` and `thread/start`, OpenCode health, `POST /mcp`, `POST /session`) has a 60 second deadline (`LEADER_START_TIMEOUT_MS`); a turn itself is not capped. A failed start, a Codex turn that is not `completed`, a final Codex `error`, an OpenCode `session.error`, a failed prompt, a dropped event stream and a child exit mid-turn each end the turn with exactly one `chatError` (a callback from a leader that is no longer the tab's current one is ignored), and the next message starts a fresh leader. Usage fills the existing context meter: Codex reports the last turn's input tokens and the model window (no cost); OpenCode reports input plus cache tokens, the cumulative message cost, and the model's context limit, which is read from `/config/providers` into memory only and never stored or logged. Past sessions read the run logs and the chat store, neither of which depends on the CLI.

An ACP leader sends `initialize` (protocol version 1, no file or terminal capabilities: the CLI uses its own), `session/new` (`cwd` = the tab folder), then one `session/prompt` per turn. `agent_message_chunk` is the reply (a new paragraph after a tool step), `agent_thought_chunk` is never shown, `tool_call` shows only its KIND as the step line (`execute`, `read`, `search`, `edit`, `delete`, `move`, `fetch`, `think`, `switch_mode`, `other`) and never its title, path, command or content, `usage_update` fills the context meter. The prompt's `stopReason` `end_turn` ends the turn; `max_tokens`, `max_turn_requests`, `refusal` and `cancelled` end it with a plain message. `session/request_permission` is answered with the `allow_once` option (else `allow_always`; with no allow option the request is refused and the chat gets a notice). Stop sends `session/cancel`, then ends the process tree. A CLI that is not signed in fails the start or the turn with `<name> is not signed in: <the CLI's own sign-in description from initialize.authMethods>`. `state.projects[].tabs[].acpLeader` is `null`, or `{ name, model }` for a tab led by an ACP CLI, with the model the CLI reported for its session (`null` before it started).

### Leader MCP bridge

`POST /api/leader-mcp/<tabId>` serves the nine fixed crew tools (see "Fixed crew tools") as a minimal MCP server to an OpenCode or ACP leader. One bridge holds every leader's entry at once, each with its own token, so any client that speaks HTTP MCP can use it with plain `application/json` replies: `initialize`, `ping`, `tools/list`, `tools/call` (a tool failure is a result with `isError: true`) and `notifications/*` (`202`, no body); any other method is JSON-RPC `-32601`. Any request carrying an `Origin` header is refused (`403`), so a web page can never reach it. Methods other than `POST` get `405`. `Authorization: Bearer <token>` is compared with `timingSafeEqual` against a fresh random 32-byte token made for that one leader instance (`401` when missing, wrong, or revoked). The body is capped at 1 MiB (`413`), and the server's normal `Host` check applies. The token lives only in that leader's runtime registration, is revoked when the leader stops or dies, and reaches only that tab's tools. It never appears in state, logs or errors.

### Advisor

A position's `advisor` (set with `setCrewAssignment`) is applied to any Claude position: a Claude leader started with the native CLI (the same condition as `--effort`), or a Claude worker run, gets `--advisor <model>` in its arguments (a value that is not a Claude model is refused before anything starts). The advisor is read when the session starts, so a change takes effect on the next leader session (after Stop, Clear, a CLI switch or a restart) or the next run. Codex, OpenCode and `acp:` positions have none (`clis[].advisor` is false).

### Limits

- An ACP leader runs in Full access only: it may edit files and run commands without asking, and Command Center cannot make it ask yet (OpenCode over ACP wrote a file without ever sending `session/request_permission`, probed 2026-10-18). `state.permissionMode` of its tab is always `bypass`; `setPermissionMode` with any other mode is refused, with `bypass` it changes nothing. The tab's saved mode stays in `settings.json` and applies again if the leader is switched to Claude, Codex or OpenCode. An ACP CLI may sit on any seat. A crew position on one is started as a worker (the brief is its one prompt; the run is done when the prompt ends normally; Stop ends it as stopped); its permission requests are refused when the position is read-only, and its read-only is not enforced. Its model is the CLI's own and cannot be changed from here; `steer` is not possible (the message is handed back as the next turn).
- Codex with `untrusted` asks only for commands it does not consider safe. Probed on Windows: `node -e "...writeFileSync..."` was asked, while `echo second > two.txt` was not asked and wrote the file even with a read-only sandbox. Ask and Plan on a Codex leader are only as strong as Codex's own classifier, and **Codex's read-only sandbox is not a boundary**: a Codex worker is treated as able to write.
- OpenCode `plan` denies edits but still asks for shell commands, and an allowed command can write.
- An OpenCode leader reads, globs, greps and lists without asking in Ask, Accept and Plan (Bypass allows everything). Reading a `.env` file and anything outside the tab folder (`external_directory`) still asks, and so does everything else.
- The advisor is Claude-only (a seat on another CLI has none).
- Switching a leader's CLI starts a fresh session: the old CLI's conversation is not carried over (the chat log stays, and the next leader reads the saved handover).
- A Claude leader applies a model change live; Codex and OpenCode apply it from the next turn. A Codex or OpenCode leader reads the seat's saved effort on every turn.
- A Codex turn keeps the approval policy it started with, so a permission-mode change while a Codex turn runs is refused ("Finish or stop <leader>'s current turn first, then change the mode.") and the chat is not stopped. OpenCode applies a mode change live.
- A failed Codex or OpenCode turn (error, failed or interrupted turn, refused prompt, unanswerable permission request) reports once and ends that leader's process; the next message starts a fresh session.

### Fixed crew tools

The leader of a fixed tab has exactly nine tools, served the same way on all three CLIs (SDK MCP, Codex `dynamicTools`, the OpenCode/ACP bridge). Each call checks that the leader instance is still the tab's current one and that workspace and task recovery are ready; a call from a replaced leader is refused.

- `get_fixed_task`: reads the saved task, its approval state and the identified execution reports. Its response remains `{ task, executions }`; each journal execution's `processEnded` means the app confirmed the whole process tree ended. Read before every change.
- `finish_fixed_task { expected, reason }`: explicit current-Leader-only completion, with a non-null expected task identity and a nonempty reason of at most 8192 characters. Revalidates owner scope/required rough approval, current content, task and source identity, checks, fresh ordinary/final review, finding triage, successful verified approved shipping and every saved execution version. Interrupted/unverified/unknown-ended work, active journal reservations, unconsumed successes, runtime runners, Git operations, cleanup, saving and open approvals stay held. Empty shipping is legal. Nothing executes automatically. A successful reply is `{ task: null, taskId, manifest }`, followed by state with `fixedTask: null`; ordinary `get_fixed_task` still returns `{ task: null, executions }`. The calling Leader's own active turn is permitted.
- `list_task_archives { kind, cursor, limit }`: current Leader's own tab only, `kind` is `task` or `execution`, `cursor` defaults to null and `limit` defaults to 50 (1-50). Returns `{ items, nextCursor }`: task items are `{ id, kind:"task", scope, completedAt }` from the verified task plan and manifest; execution items remain `{ id, kind:"execution" }` in stable ID order without an aggregate index or total-history cap.
- `get_task_archive { kind, id }`: own-tab verified read. A task returns `{ task, executions, manifest }`; an execution returns its immutable server-bound facts, including assignment, consumption/end/status and log reference. Unfinished, conflicting, foreign or corrupt archives refuse.
- `reconcile_task_execution { expected, runId, reason }`: for journal-backed work, the current Leader abandons only the identified interrupted execution or failed finalization, using the saved matching journal `processEnded: true` fact from the app's whole-tree callback. A root exit, task `processEnd`, model reason or owner release cannot replace that fact. It refuses a live runner, unfinished Git operation or cleanup, stale identity, foreign reservation and unknown tree end. It saves a brake before reconciling the task, then marks only that journal entry failed and consumed, clears only its reservation, and retires only its ended Git operation after both publications succeed. A failed publication stays held; read the current task and retry reconciliation, never the external action. Existing corrupt/capped tasks can still refuse. No HTTP recovery endpoint or browser recovery message exists.

Recovery can also abandon ended, unused planning/triage reports from initial taskless planning or an earlier version of the same task. Consumed reports and accepted provenance, including coordinator sessions, cannot be abandoned. Unknown process end stays held. The current Leader may explicitly cancel an authenticated task-only reservation with no journal or archive admission and no runtime, persisted launch or positive result contradiction. Browser intent requires the exact pending request session; direct Leader intent requires the retained original action receipt digest. Cancellation records failed, confirmed no launch, unverified history with empty evidence and no result revision. Cold normalization preserves the saved stage for proven unadmitted reservations while marking their execution interrupted; historical interrupted stages recover conservatively to planned only after all unresolved work is settled. A failed publication retains the brake. A fresh retry after durable publication changes no bytes or revisions. Completion still requires genuine checks, reviews and approved shipping. Missing journal/archive history that was externally deleted without remaining contradictory facts is outside this app-lifecycle proof; this is not universal recovery.

A journal-admitted refused start may also be reconciled explicitly when the task is still reserved with unknown end, the journal is failed, ended and unconsumed with no log, and the original action receipt, current disk and runtime facts prove the start was refused. Duplicate journal IDs are refused before any admission or pruning; retry reconciliation rather than relaunching an old ID. This does not release launched or ordinary unknown-ended work.

**Worker reports.** The server scans the whole server-bound run log as a stream for the `CC_REPORT_BEGIN` / `CC_REPORT_END` block. Only the block's payload is capped (256 KiB, `REPORT_MAX_BYTES`), never the transcript around it. The same report echoed again, with LF or CRLF line endings, counts as one report. Blocks that differ, a nested or unfinished block, an oversized payload, text that is not valid UTF-8 and a log that changes while it is read are refused.

**Normal shutdown.** Worker admission closes first. Then leaders and runners are stopped and the Git work, the workers and the HTTP close (7 s) are drained in parallel, so their budgets are not added up (workers about 52 s: 5 s kill grace, 0.75 s pipe drain, the 41 s sweep cap and a 5 s margin). A worker counts as finished only when its whole process tree end is confirmed and its journal callbacks completed. A worker whose end is not confirmed is never assumed ended: the server logs `Worker shutdown INCOMPLETE` and exits 1, and unknown-ended work stays held after the restart. The desktop shell force-kills a server that is still alive only after 125 s (`KILL_GRACE_MS`). The start-up orphan sweep's count (`[cleanup] stopped N processes left by an earlier server`) is a log line only: it cannot unlock or release a fixed-task journal; only `reconcile_task_execution` can.


- `begin_planning { expected, brief, triage? }`: asks the assigned Planner for a plan, or with `triage` for a sorting of findings.
- `accept_planner_report { expected, runId }`: accepts only the structured report bound to the identified ended Planner run. If the saved task already records that Planner acceptance and only the consumed journal publication failed, retry finishes that publication without reapplying the plan or triage. Proven consumed retries write nothing. Accepted history cannot be abandoned.
- `request_task_action { expected, kind, route, change, brief, reservedExecutionId? }`: asks for one action (`assist`, `rough`, `build`, `polish`, `check`, `visualCheck`, `inspect`, `review`, `checkpoint`, `fix`, `final`, `commit`, `push`, `publish`) through the approved task gate. The server picks the assigned position and starts a fresh run; shipping is limited to the approved scope.
- `verify_task_evidence { expected, runId, checkName? }`: records the leader's own verification of an identified successful, ended, current run.

`expected` is `null` (no task yet) or `{ taskId, planVersion, recordRevision }` and must match the saved task. The brief is at most 200000 characters. Only one fixed execution is reserved or running at a time, across the app. A reviewing action takes the assigned reviewer, or another assigned reviewer of a different company than the actual writers when there is one, and the answer says why. No position launches another position, and a worker has no crew tools.

Fingerprinting accepts at most 4096 entries and 64 MiB aggregate content, with metadata preflight and no partial acceptance. Re-planning scans the proposed coverage, not the abandoned old coverage. Cancellation and reconciliation preserve the last valid revision. Ordinary approvals, actions, evidence and completion still require their content-freshness checks.

The fixed-crew Git runner disables automatic maintenance per command with `gc.auto=0` and `maintenance.auto=false`. Owner Git maintenance remains governed by the owner's own configuration. Hooks, signing, filters, credentials and strict owned-tree cleanup stay active. Native Windows acceptance is opt-in (`CC_P26_RUN2_NATIVE=1`) and required outside the write sandbox; mocks do not replace it.

**Permissions at launch.** The server checks the tab's saved mode and the live mode of the leader's session at the moment of the call and again after any approval. In **Plan** the call is refused (`Switch out of Plan mode before starting fixed work.`). In **Ask** (the saved mode, or a live mode of `default`) it first raises an approval with `tool: "fixed-action"` whose summary starts with the trusted action, actual selected position, CLI/model/effort and target folder, followed by the leader-written brief (checkpoint, commit and push name server Git as the executor); Deny, or the leader stopping, starts nothing and the leader is told `The owner denied this action.`. In **Accept** and **Bypass** it starts at once. If the assignment or the permission changed while waiting, nothing starts and the leader must request it again. This applies to every action, whatever the position's CLI or write permission. A launch refuses a position with no model (`<Position> has no model. Choose one in Settings before continuing.`).

Leader tools reach only the leader's own tab. A run's result is read from its structured report; the server relaunches nothing by itself.

**Archive durability and limits.** Completed tasks live under `<dataRoot>/tasks/finished/<tabId>/<taskId>/` as exact original `source.json`, completed `task.json`, `manifest.json` (version, identities, completion metadata, byte counts and hashes) and a final manifest-bound `complete.json` receipt. Execution archives are `tasks/finished/<tabId>/_executions/<runId>.json`; logs/evidence references remain intact. No files leave the existing private `tasks/` boundary. All paths are derived from validated IDs, links are refused, reads are bounded before parsing, and immutable publications reuse an existing file only when its bytes match.

Rollover first persists `tasks/<tabId>.rollover.json`, then publishes/verifies the task and execution archives, rechecks live source identities, atomically writes exactly `null\n` to the live task, removes only the exact archived journal rows, verifies both, publishes the completion receipt, retires that transaction and updates cache. Startup `initializeFixedTasks -> TaskStore.get` resumes the transaction before cache lookup or interruption normalization. Partial rollover blocks new actions; recovery never rolls back over newer task/journal state and never retries external work.

Task list/request/byte, report and fingerprint limits remain active. Valid completed tasks at a limit need no extra live append to archive. Unfinished tasks may still reach protective limits; a refused oversized write preserves the last published file, and existing malformed/future/over-limit files remain held. Before a new journal reservation, eligible settled rows are individually archived and verified before pruning; unconsumed successes, active/interrupted/unknown-ended records, live runners and unsettled Git cannot be reclaimed. Capacity above 2,000 entries refuses before task reservation/spawn. The existing owner Release path does not confirm fixed journal end and remains insufficient for archival.

The read-only Finished tasks view initially shows 3 rows and requests pages of 50. It lists verified scope, finish date, ID and Open controls. It reads the saved plan, evidence and historical runs without restore, replay or delete. The current task page displays **No plan yet** after rollover.

## HTTP paste-image endpoint

`POST /api/paste-image` accepts `image/png`, `image/jpeg`, or `image/webp` with a body up to 12 MiB and requires a valid `X-Request-Id`; there is no legacy route that accepts a missing id. The id is echoed in the response, and the upload status is in `state.settings.uploads` (at most 32 entries). A request refused for its Host or Origin records no status. Before writing, the server resolves the real scratch directory and data root and refuses a directory outside that root. The file is written through the resolved directory under `<data root>/scratch/`.

Your own picture is the client preference `avatar` (`updateClientPref`: a preset name or an image data URL up to 512 KB); it is not an upload and writes no file. There is no `POST /api/avatar`: it is refused (`403` without the app key, `405` with it) and writes nothing. `GET /api/avatar/<filename>` still serves an image uploaded by an older version, only when the name is `avatar-<uuid>.png|jpg|webp` and the real file stays inside `<data root>/avatars/` (a junction pointing outside is refused). Nothing creates or deletes files there; a workspace recovery backup copies them as they are.

`POST /api/paste-file` accepts up to 20 MiB, a valid `X-Request-Id`, and a percent-encoded `X-File-Name`. Allowed extensions: `.txt`, `.md`, `.markdown`, `.pdf`, `.csv`, `.json`, `.jsonc`, `.yaml`, `.yml`, `.toml`, `.xml`, `.html`, `.htm`, `.css`, `.scss`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.py`, `.rs`, `.go`, `.java`, `.c`, `.h`, `.cc`, `.cpp`, `.cs`, `.swift`, `.kt`, `.sql`, `.sh`, `.ps1`, `.bat`, `.log`, `.diff`, and `.patch`. The server resolves scratch and the data root before writing and refuses a scratch directory outside that root. Files are stored through the resolved scratch directory with generated names; the response is `{ "path", "name", "requestId" }`. Chat accepts only generated paths contained in scratch, and the leader prompt names files it may read.

All upload routes enforce the same Host and Origin checks. `GET /api/paste-image?path=<encoded path>` serves only generated image files inside scratch. The server serves static files with `GET` and `HEAD`.

Settings, the changes panel and the agent status calls use one injected `runCli(bin, args, { timeoutMs })` runner (CLI discovery of models and effort at start-up has its own bounded runner, which resolves the real CLI path first, runs it through the shell, and on a timeout ends its whole process tree with the System32 `taskkill.exe`). `runCli` spawns an argument array with `shell: false`, `windowsHide: true` and a timeout. On Windows it resolves the real launcher from PATH; a `.cmd`/`.bat` (npm, codex, opencode) runs through `%ComSpec%` (`cmd.exe /d /s /c`) with every part double-quoted and no `call`. An argument containing `%` is handed over through an environment variable that cmd expands once as plain text. An argument or launcher path containing `"`, `!`, CR, LF or NUL, or a launcher path containing `%`, is refused rather than escaped (`unsupported characters in command arguments`). When a Windows command times out, the runner invokes `taskkill.exe /pid <pid> /T /F` from the Windows System32 folder by its absolute path, with argv, and waits for the command process to close or a bounded confirmation wait before returning code 124. If Windows denies `taskkill`, it snapshots and terminates descendants, then reports whether tree exit was confirmed. MCP and plugin names must start with a letter or digit. Tests inject a fake runner and temporary HOME/USERPROFILE values; inventory tests never read the real user homes. GitHub output is reduced to connected state and account name, never a token.

## Tool approvals

Every tab in `state.projects[].tabs[]` carries `pendingApprovals`, an array of
`{ approvalId, tool, summary, createdAt, askedBy }`. `createdAt` is epoch milliseconds. `askedBy` is `{ kind: "leader", slot, name }`, the leader that is asking.
The summary is the whole text the user is answering: every changed file path (one per line) for a file approval, the full command, the trusted operation metadata followed by the leader-written brief for a fixed action, or JSON for other tools. Line breaks are kept and the page shows it scrollable. A summary over 20000 characters is cut with a final line `... (N more characters not shown)`. When a Codex file approval also asks for write access to a folder (`grantRoot`), the line `Also asks for write access to: <folder>` is added. Multiple calls may wait at once. State survives browser
refresh and reconnect, but approvals are never persisted across server restarts.

`answerApproval` takes `{ requestId, tabId, approvalId, allow }`, with a required
request ID and a boolean `allow`. Success sends `actionResult` with
`action: "answerApproval"`, the same request ID, tab ID and approval ID. Refusal
sends `error` with the same request ID and tab ID and a readable message. A
missing approval, wrong tab, dead or replaced leader is refused without changes.
Stopping a leader, aborting its tool signal, removing its tab/project or shutting
down denies all affected approvals and removes them from state.

Every leader registers a `PreToolUse` hook with `timeout: 86400`. The hook asks
when the SDK's live `permission_mode` is `"default"` OR the tab's saved mode is
`ask` (the server passes the saved mode in), so a subagent's own `permissionMode`
or a mode the SDK lands in after ExitPlanMode cannot skip the question while the
tab is saved as Ask. Then Edit, MultiEdit, Write, NotebookEdit, Bash and
PowerShell wait for Allow or Deny. This hook fires even when user settings
pre-allow those tools. Other tools, and other permission modes on a tab not
saved as Ask, return an empty hook result. `canUseTool` uses the same approval flow whenever
the SDK itself asks for permission, including commands in accept mode.
Denials say `The user denied this.`; internal errors and aborts deny as well.

A fixed action (`begin_planning` and `request_task_action`) is gated where the launch happens, by the tab's saved mode and the live mode of the leader's session; see "Permissions at launch" under "Fixed crew tools". The panel and the Waiting card read "<leader name> wants to use fixed-action" for such an approval.

The selected tab shows the oldest approval in a panel directly above the composer.
It stays visible until answered, without a scrim, focus trap or Escape dismissal.
Its Waiting card selects the tab and focuses the panel. Allow and Deny buttons
disable while an answer is in flight and the panel shows refusals. Pending tool
approvals are intentional user waits, not stalled worker runs; the worker stall
monitor only tracks crew subprocess runs. Chat and Save refuse with
`Leader is waiting for your answer on a change` while blocked by an approval,
including an approval that appears while Save is waiting for a turn. Save's own
Write in Ask mode is not refused: an approval raised by Save's own leader turn
makes Save wait for the answer (its 30-second timeout re-arms while an approval
is pending and resets to a full 30 seconds when that approval settles). After
Allow the handover is written and the chat is marked saved;
after Deny Save fails with `leader could not save the handover`. An approval that
was already pending before Save started refuses Save at once.
In the panel, every new approval starts a 400 ms settle period, including first
appearance, an idle gap and a tab switch. Same-ID broadcasts do not restart it.
Pointer-down or non-repeated key-down must start after settle on the same ID
still displayed at activation. Pointer captures belong to the pointer that
began them; another pointer cannot activate or erase them. Multi-clicks and held
keys cannot answer a replacement.
